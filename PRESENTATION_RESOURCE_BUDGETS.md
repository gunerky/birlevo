# Presentation PDF and slideshow resource budgets

16 October 2026. Development validation only: version 0.1.11/code 12 and frozen signed packages are unchanged. This work builds on the photo-PDF changes in PR #11.

## Implementation

`DiskPdfWriter` now owns the shared private scratch, encoded page/resource cloning, cancellation checks, guarded output, descriptor sync and atomic rename for photo and presentation PDFs. It reads only pages generated by the application. External PDFs still use the existing isolated workers; their permissions and 64 MiB stream budgets are unchanged. Image streams receive no second encoding; presentation text, vectors, native shaping, geometry, footers and font resources remain.

Photo PDFs still close each native page individually. Presentation PDFs retain a small native group, selected from measured heap/system headroom and available working space, with a maximum of eight pages. This allows a group to share native font subsets. A single native document retaining every slide grew steadily; an initial one-page variant reduced retention but duplicated font subsets excessively. The final bounded-group variant avoids that extreme while preserving every slide and its image edge. It does not reduce the page count, crop content or change quality to fit a budget.

`MediaResourcePlan` has saturating source-plus-destination composition estimates and a pure page-group policy. `SlideImages.decodeMemory` uses the actual platform decoder path: exact target dimensions where supported, legacy power-of-two decode dimensions otherwise. Presentation video frames and photo slideshow rasters admit both the decoded source and destination. Private software canvases detach after drawing so they do not unnecessarily retain bitmap pixel storage; returned UI bitmaps remain valid and are not forcibly recycled.

Slideshow creation admits the requested codec-frame estimate and VBR disk estimate, then checks actual space before every PNG and guards PNG writes. A 250 ms child monitor checks space while the native encoder writes by path. Pressure cancels the existing Transformer owner and uses its normal cleanup path; requested size/bitrate and disabled encoder fallback remain. Partial PNGs, working MP4s and disposable outputs are removed on cancellation/failure. Existing results, private input snapshots, project/session schemas and copy consent remain intact. Save/export copies also use the existing guarded stream policy.

## Measurements and file tradeoff

The synthetic presentation contains a separate 1024×768 image, heading and body per slide; the PDF keeps its existing 960×540 vector geometry and 1024 image-edge policy. The video has 20 presentation frames at 500 ms each, 1920×1080, 30 fps, AVC and no audio. No photographic-noise or arbitrary complex-font performance claim follows from these samples.

| Run | Highest native at page-progress samples | Additional native sampling peak | Java used at progress samples | PSS at progress samples | PDF generation interval |
| --- | ---: | ---: | ---: | ---: | ---: |
| API 28 original, 24 slides | 76.3 MiB | not measured | 3.5 MiB | 186.8 MiB | 1.35 s |
| API 28 fixed, same 24 slides | 7.0 MiB | 31.0 MiB | 4.1 MiB | 158.0 MiB | 1.22 s |
| API 28 fixed, 100 slides | 7.7 MiB | 31.7 MiB | 4.3 MiB | 157.0 MiB | 4.96 s |
| API 24 fixed, 100 slides | 6.3 MiB | 7.0 MiB | 32.9 MiB | 57.8 MiB | 4.39 s |
| API 36 fixed, 100 slides | 10.8 MiB | 38.2 MiB | 11.0 MiB | 136.3 MiB | 27.24 s |

The additional sampler reads allocated native bytes every 10 ms; it can still miss allocation peaks. The original run had only page-progress samples, so its full peak is unknown and at least the observed 76.3 MiB. Completed-page observations alone hide the native group's internal peak; the separate sampler is retained for this reason. These are single instrumentation runs, not a latency benchmark; intervals include per-page memory/PSS sampling overhead. Android bitmap accounting differs across versions; do not rank devices by one column. Preview/GPU/codec allocations are not fully represented, and no physical-device FPS, battery or RAM guarantee is made.

The 24-slide original PDF is **107,304 bytes**, the discarded one-page-per-document variant was 764,216 bytes, and the final grouped file is **169,319 bytes**. Font subsets still repeat between groups, so bounded memory trades additional disk I/O and some file overhead for lower retained memory. This is new document creation, not a claimed compression success. The file-specific regression bound is below three times the original for this fixture, not a universal size guarantee. Independently rendered pixels for all 24 pages, extracted text and embedded image pixels match the original exactly. The 100-slide outputs are 721,445 bytes on API 28, 731,280 bytes on API 24 and 840,357 bytes on API 36.

Slideshow progress samples did not demonstrate a reliable native-memory reduction (about 28–30 MiB in API 28 runs). Its concrete gains are explicit admission, early pressure failures and cleanup/retry protection; no speed/RAM improvement is claimed for the encoder. Independent full video decoding preserves resolution, duration, frame rate and silence.

## Environment and remaining work

All device tests use x86_64 emulators. API 24/28 use 2 GiB RAM / 256 MiB VM heaps and enabled OpenGL. API 36 uses a fresh dedicated emulator with 3 GiB RAM / 228 MiB VM heap, a configured 4 GiB data partition, host graphics and Vulkan disabled. Its fresh boot followed filesystem repair after host disk exhaustion; its timings are not directly comparable to earlier runs. Host disk exhaustion initially prevented API 24 from starting. Only stopped, dedicated QA generated userdata was reset after exact-path/process checks; the API 24 generated disk was also removed after evidence collection to recover space. Source files, signed artifacts, AVD definitions and host evidence were retained. These are environment recovery steps, not guest storage-pressure tests; application pressure tests use injected measurements.

Next: profile image-heavy external PDFs near the 128 MiB boundary and their isolated-worker object/scratch budgets. Worst-case fonts, 32-bit/ARM runtime, low-memory physical devices, all providers and real battery/FPS remain unmeasured. Persisted project keys, URI authorities/roots and output quality choices are unchanged.
